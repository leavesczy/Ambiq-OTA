# Ambiq OTA 实现说明

本项目的固件升级逻辑依据 Ambiq 文档 **OTA-Firmware-Update-Example-App-Note.pdf** 中的 **AMOTA（Ambiq
Micro Over-The-Air）** 协议实现。手机作为 BLE GATT Client，通过固定 AMOTA 服务向设备下发命令与固件数据。

## 总体流程

一次完整升级按固定顺序进行：

1. 建立独立 GATT 连接并完成服务发现、通知开启、MTU 协商
2. 发送固件头（HEADER）
3. 分块发送固件数据（DATA）
4. 请求设备整包校验（VERIFY）
5. 请求设备复位以应用新固件（RESET）
6. 断开连接（设备侧随后重启）

协议命令顺序不可打乱；每一条逻辑命令发出后，都必须等待设备通过 Notify 返回成功状态，再发送下一条。同一时刻只允许一次升级会话。

## 扫描与设备选择

升级前使用系统 BLE 扫描器搜索附近设备：

- 优先取广播中的设备名，否则取系统缓存名
- **两者皆空则忽略**，不进入可选列表
- 用户选中带名字的设备后，再进入 OTA 流程

## GATT 通道

| 用途             | UUID                                   |
|----------------|----------------------------------------|
| AMOTA Service  | `00002760-08c2-11e1-9073-0e8ac72e1001` |
| RX（手机 → 设备）    | `00002760-08c2-11e1-9073-0e8ac72e0001` |
| TX（设备 → 手机）    | `00002760-08c2-11e1-9073-0e8ac72e0002` |
| CCCD（开启 TX 通知） | `00002902-0000-1000-8000-00805f9b34fb` |

- 命令与数据一律写入 **RX**，写入类型为 **Write Without Response**
- 设备应答一律通过 **TX Notify** 返回
- 连接使用 `TRANSPORT_LE`，连接成功后会请求高连接优先级

## 连接准备

在发送任何 AMOTA 命令之前，依次完成：

1. 按 MAC 地址建立 GATT 连接
2. 发现服务，定位上述 Service / RX / TX
3. 开启 TX 的 Notify，并向 CCCD 写入开启通知标志
4. 请求 MTU **247**；单次 ATT 可写载荷取 `min(mtu - 3, 237)`，协商失败时回退为 **20**
5. 全部就绪后才进入协议发送阶段

连接准备超时为 **30 秒**。准备阶段对外进度记为 **0%**。

## 命令帧格式

写入 RX 的每一条 AMOTA 逻辑帧（小端）为：

```
[lenLE 2 字节][cmd 1 字节][data N 字节][crc32LE 4 字节]
```

约定：

- `len = N + 4`，只表示 data 与 crc 的合计长度
- `cmd` 为命令码
- `crc32` 只对 `data` 计算；无 data 时 crc 填 **0**
- CRC 使用文档规定的查表 CRC32 算法

一条逻辑帧可能大于当前 ATT 可写长度。实现上会按当前 payload 上限切成多段连续写出；**整条逻辑帧写完后**
，再等待对应的 TX Notify，而不是每段 ATT 写都等一条协议应答。

单次 GATT 写超时为 **3 秒**。

## 命令码

| 命令     | 码值 | data 内容              |
|--------|----|----------------------|
| HEADER | 1  | packed 固件前 48 字节     |
| DATA   | 2  | 固件数据，单包最多 **512** 字节 |
| VERIFY | 3  | 无                    |
| RESET  | 4  | 无                    |

## 设备应答

TX Notify 布局：

```
[len0][len1][cmd][status][可选附加数据…]
```

- `status == 0` 表示该命令成功
- 非 0 为协议错误（如 CRC 错误、非法头信息、包长度非法、缓冲不足、Flash 不足、Flash 写失败等），升级立即失败
- HEADER 成功且应答长度不少于 8 字节时，字节 `[4..7]` 为小端 **续传偏移**（设备已成功写入的固件字节数）

普通命令应答超时 **3 秒**；VERIFY 超时 **5 秒**。

## Packed 固件格式

升级文件必须是文档所述的 packed 固件：

1. 前 **48** 字节为头
2. 原始固件长度位于头内字节 **`[8..11]`**（小端无符号整数）
3. 第 48 字节之后为固件本体

头长度不足 48 字节，或解析出的固件长度 ≤ 0，则拒绝升级。用户选择的固件会先流式缓存到本地，再按文件路径参与升级。

## HEADER 阶段

1. 从固件文件读取前 48 字节
2. 解析固件总长度
3. 组装并发送 HEADER 命令
4. 等待成功 Notify；若续传偏移 `> 0`，在输入流中跳过对应字节，后续 DATA 从该偏移继续

本阶段进度保持 **0%**。

## DATA 阶段

从当前文件位置起循环发送，直到已发送字节数达到固件总长度：

1. 每次最多读取 512 字节作为 DATA 的 data
2. 发送 DATA 命令并等待成功 Notify
3. 按「已确认字节数 / 固件总长度」将进度线性映射到 **0%～94%**

用户取消时会停止继续发包并结束会话。

## VERIFY 阶段

发送无 data 的 VERIFY 命令，等待设备整包校验成功。进度记为 **96%**。

## RESET 阶段

发送无 data 的 RESET 命令，**必须收到成功 Notify** 才视为升级成功，进度记为 **98%**。随后进入成功状态 **100%**，并断开 GATT。设备收到复位后会重启并加载新固件。

## 进度阶段一览

| 阶段   | 含义                | 进度     |
|------|-------------------|--------|
| 准备连接 | GATT 连接、服务、通知、MTU | 0%     |
| 发送头  | HEADER            | 0%     |
| 发送数据 | DATA（按已 ACK 字节）   | 0%～94% |
| 校验   | VERIFY            | 96%    |
| 复位   | RESET             | 98%    |
| 成功   | 协议完成              | 100%   |

失败或取消时保留当时进度，并给出对应错误原因。

## 取消与结束

- 取消会置位停止标志，打断后续发包，并断开当前 GATT
- 会话结束（成功、失败或取消）后都会关闭连接，避免占用设备
- 离开升级页时，若仍在升级中会先取消再清空界面状态
